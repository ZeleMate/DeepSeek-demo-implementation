# The hardened profile turns off bash and PTC, and every defence fails closed

dsh's sandbox limits only file writes. It sets no limits on network or reads, so the shell tool could `curl` anywhere and file tools could read `~/.ssh`. Rather than build a network sandbox, the hardened profile **turns off the bash tool and PTC mode**. Jobs get dedicated tools instead (e.g. a gitleaks tool for the secrets filter).

The profile starts from: a read-only sandbox; approval set to `ask`, which is denied when no one can answer (as in headless runs); telemetry off (the `session-telemetry-otel` row disabled, `session-log-deepseek` off, and `DSH_TELEMETRY_DISABLED=1` exported as a second lock, because a triggered upload sends the whole session unredacted); and only the MCP servers under test.

Six defences sit on dsh's tool pipeline, and **each one fails closed**: a detector error counts as a hit, and an unanswerable approval counts as a denial.

1. **Policy plugin** (`tools/pre-execute`): a host allowlist for `web_fetch` URLs and outbound MCP arguments (OpenRouter, OpenAI, Tavily, `127.0.0.1`); a read allowlist for file tools (workspace and scanned repo only, always denying `$DSH_HOME` and any `.env*` outside the workspace); and the taint rule, which escalates outbound calls to `ask` once untrusted content has been read in this session (ADR 0013).
2. **Injection filter** (`tools/post-execute` on `web_fetch`, file reads and `mcp__*`): regex rules plus a Decisions API predicate. At 0.5 or above it wraps the content as untrusted data and sets the taint flag; at 0.9 or above it blocks by replacing `value`, not just `content`.
3. **MCP pinning guard** (`ctx.tools.guard`): hashes each tool's name, description and schema plus the server instructions into a committed lockfile. New tools need approval on first use, and changed tools are refused until re-approved. It refuses at call time, and a `system-prompt/assemble` listener in the same plugin keeps a changed tool out of the prompt: its description is replaced with a fixed "withdrawn" text, and an `mcp:<server>` instructions section whose text changed is dropped. The listener's returned tool list is what dsh sends to the model, so no upstream change is needed ([prototype](https://github.com/ZeleMate/DeepSeek-demo-implementation/tree/prototype/26-mcp-pin-hide/prototypes/26-mcp-pin-hide), [#26](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/26)). Replacing beats hiding: a hidden tool fails with `UNKNOWN_TOOL`, and the model loops trying alternatives.
4. **Read allowlist**: part of the policy plugin; listed separately because reads are otherwise unconfined.
5. **Canary secret**: a fresh random value per run, planted in the workspace `.env` and a fake config file. Its variable name must match no route's `apiKeyEnv` (e.g. `CANARY_SERVICE_TOKEN`): dsh reads the workspace `.env` as a key fallback, so a canary named `OPENROUTER_API_KEY` would be sent to OpenRouter as the key whenever the real one is missing. It is detected in outbound arguments (denied), in the model stream through `llm/stream` (turn flagged), and in the audit log.
6. **Audit**: dsh's session log, stored uncompressed (`compression: none`), plus one small audit plugin, `@zelemate/dsh-audit`. The session log already records tool calls and results, approvals, per-step tokens and which model answered (`responseModel`, `responseId`). It does not record our defences' decisions, so the audit plugin writes `plugin:zelemate-audit/*` records through dsh's `appendPluginRecord()` for every policy denial, injection-filter score, taint change, pin decision and canary hit. It also writes a per-run JSON summary (models, tokens, denial codes, canary counts) for Promptfoo to assert on. These records never reach the model. `appendPluginRecord()` is marked experimental and survives log-format migrations only on a best-effort basis, so it is rechecked at every dsh upgrade (ADR 0001).

_Amended 2026-10-23 by ADR 0013 ([#90](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/90)):_ defences 1–5 no longer deny on their own. They feed one policy decision made at `tools/pre-execute`, and a monotonic guard enforces the hard denials, so "fails closed" is one rule instead of six. Defence 6 becomes the hash-chained ledger. The hardened profiles also turn off dsh's subagent tools and cap tool calls per turn.

_Amended 2026-11-07 ([#121](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/121)):_ bash and PTC are not the only tools whose output reaches the model outside the turn that started it. In dsh rc.2 a background job's output and a subagent's answer arrive later, as a user message in a new turn, and no tool hook sees a subagent's answer. So both hardened bundles turn off the async rows too: `jobs`, `tool-jobs`, `tool-bash`, `tool-pwsh`, `tool-subagent`, `tool-subagent-fork`, `tool-subagent-control`, `tool-subagent-list-agents`, `workflow-ptc` and `tool-workflow`. They also turn off `goal`, `goal-round-driver`, `command-goal` and `tool-goal`: each goal round re-sends a model-written objective as a new message, so a goal set under injection would return every round. dsh's spill policy cuts a tool result over 12,500 tokens and leaves the rest in a `dsh-spill-*` file, so the injection filter, when it lands ([#67](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/67)), treats a read of that file as the original tool's result. If a later profile turns async back on, the filter must also run at `agent/pre-step` on claimed messages whose source is not `user`, and on `job_output` results (research/dsh-async-taint.md).

_Amended 2026-11-08:_ the rows above come off now, ahead of the defences, because the public repo's quick start runs these bundles. Both bundles also turn off `ptc-runtime`, and fix `sandbox-policy` at `read-only` and `approval` at `ask` in the bundle, so `DSH_PERMISSION_MODE` can't widen them. Both turn off `agent-instructions`, `skill`, `skill-filesystem` and `tool-skill`, because those read instructions from the working directory and the home folders. The job bundle turns off `tool-fs` and `tool-fs-search` until the read allowlist lands in M4: reads are unconfined and that profile's model is remote. The red-team bundle keeps its file tools, because its model is local and it has no shell or network tool. No attack set exists yet, so no `eval/results` file rides with this (ADR 0011).
