# Landscape: what do defensive and AppSec security agents do today?

Research for [#19](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/19) (map: [#1](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/1); feeds [#22](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/22)). Checked **2026-10-18**.

Markers:

- **[verified]**: read on the primary source (paper, repo README, dataset card or official docs) on the check date.
- **[secondary]**: seen only in a press article, aggregator or search excerpt.
- **[unverified]**: from memory or inferred; confirm before relying on it.

Prices are OpenRouter's live `GET /api/v1/models` listing on the check date, in USD per 1M tokens (input / output). Listed prices are often the cheapest endpoint, and real cost floats across endpoints (see [`research/openrouter-models.md`](https://github.com/ZeleMate/DeepSeek-demo-implementation/blob/research/openrouter-models/research/openrouter-models.md)).

## TL;DR

- **Four defensive families now have agent benchmarks.** They are alert triage (SecAlertBench, Alert-Bench, SIR-Bench), log and incident investigation (ExCyTIn-Bench, AuditBench), threat intel (CTIBench, CyberSOCEval) and detection engineering (CTI-REALM, AUTOSIGMA). **The best frontier scores are still modest:** ExCyTIn tops out at 0.606 reward, CTI-REALM at 0.637, and CyberSOCEval's threat-intel accuracy at 43–53%.
- **The AppSec families are more mature.** Benchmarks with execution-based checks exist: BaxBench (generate secure code), SEC-bench, AutoPatchBench and CVEfixes (patching), PrimeVul (detection), and VEX-Bench (dependency exploitability). Real systems follow one pattern: **a symbolic tool finds candidates, an LLM explains or patches them, and a deterministic check verifies the result.** Examples are Copilot Autofix (CodeQL plus an LLM), IRIS (CodeQL taint specs inferred by an LLM), Buttercup (fuzzer plus a patch agent) and CodeMender (static/dynamic analysis plus an LLM judge).
- **Small open-weight models are weak zero-shot but strong on narrow, labelled jobs.** Llama-3-8B is last on every CTIBench task. Raw 7–8B models score F1 0.33–0.52 on SecretBench, but **fine-tuned they reach F1 0.97–0.99**. In ExCyTIn, Qwen3-32B scores 0.18 and Phi-4-14B 0.085, against 0.606 for the best frontier model. Vulnhuntr's maintainers report open models failing at structured output. The lesson for this harness: **give small models classification-shaped jobs, and use them as filters behind a deterministic candidate generator.** That shape is exactly where the Decisions API fits.
- **The best freely usable labelled data for a learner:** CTIBench (CC BY-NC-SA 4.0), Samsung CredData (Apache-2.0), CVEfixes (data CC BY 4.0), SEC-bench (MIT), BaxBench (MIT), SigmaHQ rules (DRL 1.1), Datadog malicious packages (Apache-2.0, but real malware), and ExCyTIn-Bench (repo MIT). Caveats: SecretBench needs a signed data-protection agreement, SecAlertBench states no license, and PrimeVul's data license is unclear.
- **Recommended first project (opinion):** a **secrets false-positive filter** or **CTI → CWE/ATT&CK mapper**. Both are cheap (under $1–2 a month), have clean labelled data, and fit Promptfoo and Decisions well. Graduate later to **Sigma rule writing with a validation loop** or an **ExCyTIn-style SQL investigation agent**.

## 1. Defensive families

### 1.1 SOC alert triage

**What agents do:** they take one alert, optionally query surrounding telemetry, and output dismiss or escalate, sometimes with a severity and a rationale.

| Project / paper | Architecture | Benchmark & reported results | Small / open-weight models |
|---|---|---|---|
| **SecAlertBench** ([repo](https://github.com/Dxsssu/SecAlertBench)) | Benchmark only. Single-shot LLM classification of normalised alert records | 8,322 alerts, 241 alert types, from 3 enterprise SOCs. 2,496 Attack / 5,826 Non-Attack. Average over 16 LLMs: TPR 79.71%, F1 70.92%, **FPR 44.13%** [verified, README] | Qwen models appear only in the latency and GPU-memory profiling; the README gives no per-model accuracy [verified] |
| **Alert-Bench** ([NeurIPS 2026](https://neurips.cc/virtual/2026/168137), [OpenReview](https://openreview.net/forum?id=w96THD65JD)) | Interactive: the agent searches telemetry through a fixed tool interface, then returns dismiss or escalate | 1,247 alerts, 6,235 investigations, from a 4-day multi-stage scenario. Every configuration misses **at least 40.4%** of attack alerts. "Revision" stages overturn more correct decisions than they fix. More compute did not mean better triage [verified, abstract] | Model not named in the abstract |
| **SIR-Bench** ([arXiv 2604.12040](https://arxiv.org/abs/2604.12040)) | Incident-response agent. Telemetry is generated by replaying incidents in the cloud ("OUAT"). An adversarial LLM judge requires forensic evidence before it credits a finding | 794 cases from 129 incident patterns. The authors' own agent gets 97.1% TP detection and 73.4% FP rejection [verified, abstract] | Not stated |
| **AiSOC** ([repo](https://github.com/beenuar/AiSOC)) | Kafka event spine, then enrichment, then LangGraph investigator agents. Prompts and tool calls are logged and replayable. Has a deterministic no-LLM triage mode | Own claims only | [secondary, README via search] |
| **Tracecat** ([repo](https://github.com/TracecatHQ/tracecat)) | Open-source SOAR (workflows plus cases) with agent features and an MCP server. Not an AI SOC by itself | n/a | AGPL-3.0 [secondary] |
| Databricks specialised triage agents ([blog](https://databricks.com/blog/scaling-security-alert-triage-specialized-agents-databricks)) | Vendor write-up of per-alert-type specialised agents | n/a | [secondary, not read] |

**Takeaway.** Alert triage is a binary decision with a costly false-negative side. The literature's main finding is **high FPR** in single-shot use (SecAlertBench) and **missed attacks** in agentic use (Alert-Bench). This is a natural fit for **calibrated probabilities plus a threshold you tune on a labelled set**.

**What agents do:** they answer investigation questions by iteratively querying log tables (SQL or KQL), pivoting on entities, and submitting an answer.

## 3. Cross-cutting findings

1. **Architecture that works:** *a deterministic candidate generator → an LLM judge or explainer → a deterministic verifier.* Examples: regex → LLM (secrets), CodeQL → LLM (Autofix, IRIS), fuzzer → LLM → fuzzer (AutoPatchBench, Buttercup), OSV → LLM (VEX), sigma-cli and Chainsaw → LLM (Sigma). Pure LLM review (PrimeVul) is near chance.
2. **Iteration helps, but not always.** ReAct+Reflect nearly doubled GPT-4o on ExCyTIn (0.293 → 0.563). Yet Alert-Bench found revision stages *hurt* F1, and CTIBench found chain-of-thought hurt Llama-3-8B. **So test every loop variant against a labelled set.**
3. **Small open models:** they are poor zero-shot generalists here (Phi-4 0.085 and Qwen3-32B 0.182 on ExCyTIn; Llama-3-8B last on CTIBench) and often fail strict output formats (Vulnhuntr). They are **excellent narrow classifiers once tuned or given a tight schema** (secrets F1 ≈ 0.98). Within the harness's budget, the realistic split is: **large cheap model for the agent loop, small model or Decisions API for classification gates.**
4. **Calibration matters more than accuracy in SOC work.** SecAlertBench's 44% FPR and Alert-Bench's ≥40% missed attacks are both threshold problems. The Decisions API's calibrated probabilities let you pick an operating point on a labelled set.
5. **Inputs are attacker-controlled.** Alerts, CTI reports, code under review and package contents can carry prompt injections; Anthropic's reviewer says outright it is not hardened against them. Every idea below should treat tool output as untrusted (see [#20](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/20)).

## 6. Candidate project ideas for this harness

Shared assumptions:

- dsh `llm-pi-ai` → OpenRouter for the loop.
- A `ctx.decisions` service ([#17](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/17)) for typed predicate, choice or score answers.
- Our plugins named `@zelemate/dsh-<plugin>` (ADR 0001).
- Promptfoo for eval, with the labelled set as test cases.
- **The plugin names below are proposals.**

Cost basis (live OpenRouter prices on 2026-10-18; mainstream-provider rates are higher):

- `openai/gpt-oss-20b`: $0.018 / $0.09
- `deepseek/deepseek-v4.1-flash`: $0.04 / $0.144 listed, about $0.30 / $1.20 on mainstream providers
- `z-ai/glm-5.3-flash`: $0.048 / $0.20
- Decisions API (`gpt-6-luna`): $0.10 in; $0.50 out on the OpenRouter chat listing

All costs are **estimates from assumed token volumes**, shown inline.

### Idea 1: Secrets false-positive filter (recommended first)

- **Value:** the cleanest instance of "deterministic candidates → LLM judge." It teaches thresholds, precision and recall, and masking of sensitive values.
- **Plugins:** `dsh-secrets-scan` (tool: wraps gitleaks or regexes, emits candidates plus a context window with values masked); `ctx.decisions`; built-in fs/subprocess.
- **Data:** Samsung CredData (Apache-2.0). Optionally SecretBench, after signing its agreement.
- **Eval:** Promptfoo over a stratified sample (e.g. 1,000 lines, about 50/50 T/F). Report P/R/F1 against CredData's published CredSweeper (0.859) and gitleaks (0.334) baselines. Sweep the threshold on the predicate probability.
- **Decisions API:** a **predicate**, "is this a real credential?", with a calibrated p and a tuned threshold. Compare it with gpt-oss-20b given a JSON schema.
- **Cost:** 1,000 × ~400 tokens = 0.4M input per run → about $0.04 on Decisions. **Under $1 a month** even with 20 runs.

### Idea 2: CTI mapper (CVE → CWE, CVSS, ATT&CK)

- **Value:** learn taxonomies (CWE, CVSS, ATT&CK) and when a small model is enough. Direct comparison with published numbers (Llama-3-8B, GPT-4, Foundation-sec-8B).
- **Plugins:** `dsh-cti` (tools: CWE and ATT&CK lookup from local STIX/CSV); `ctx.decisions`; optionally Tavily search to enrich CVEs (already chosen in [#9](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/9)).
- **Data:** CTIBench RCM (1,000), VSP (1,000) and ATE (60), under CC BY-NC-SA. ATT&CK STIX and the CWE list.
- **Eval:** Promptfoo; accuracy for RCM, MAD for VSP, F1 for ATE.
- **Decisions API:** a **choice** for CWE (over top-k candidates from a cheap retriever), and **choice/predicate per technique** for ATE. A CVSS vector is better as a structured LLM output; Decisions could score each metric as a choice.
- **Cost:** 2,000 items × ~600 tokens = 1.2M input per run → $0.12 (Decisions) or about $0.05 (gpt-oss-20b). **About $1–2 a month.**

### Idea 3: Sigma rule writer with a validation loop

- **Value:** a real agent loop with a **deterministic verifier**: write → `sigma check`/convert → run with Chainsaw on EVTX → fix. It teaches detection engineering end to end.
- **Plugins:** `dsh-sigma` (tools: `sigma_validate` via sigma-cli/pySigma; `sigma_run` via Chainsaw on local EVTX); `dsh-attack-kb` (ATT&CK lookup); memory plugin for the rule library. Runs in the sandbox (Docker), per [#8](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/8).
- **Data:** SigmaHQ (DRL 1.1). Hold out N rules and give the agent each rule's description and ATT&CK tags; its job is to re-derive a working rule. Event samples from OTRF Security-Datasets or SigmaHQ `regression_data` (contents [unverified]).
- **Eval:** Promptfoo with assertions: valid syntax (javascript assertion over the tool result), fires on the positive sample, silent on benign, and an `llm-rubric` judging similarity to the reference. Optionally compare with AUTOSIGMA's template-grounding trick (retrieve similar SigmaHQ rules first).
- **Decisions API:** a **predicate**, "does this rule plausibly detect technique T?", as a cheap pre-filter before running it; a **score** for rule quality as an LLM-judge alternative (only a partial fit per #17).
- **Cost:** a loop of ~6 steps × ~6k tokens ≈ 36k input per rule; 50 rules ≈ 1.8M input per run → about $0.07 listed or $0.55 mainstream on deepseek-v4.1-flash. **About $2–5 a month.**

### Idea 4: SOC alert triage copilot with calibrated escalation

- **Value:** the core SOC job. It teaches operating points (TPR against FPR) and enrichment tools, and shows why "more reasoning" can hurt (Alert-Bench).
- **Plugins:** `dsh-alert-triage` (tool: enrich, i.e. ATT&CK lookup, IP or hash reputation from a local cache; Tavily optional); `ctx.decisions`; session log for an audit trail.
- **Data:** SecAlertBench (8,322 labelled alerts; **no license, so local learning only and nothing redistributed**). Alternatively, label your own alerts from a local lab (Juice Shop and Wazuh, per [#21](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/21)).
- **Eval:** Promptfoo on a balanced 500–1,000 sample; TPR, FPR and F1, compared with the paper's 16-model averages (TPR 79.7%, FPR 44.1%). Ablate enrichment on vs off.
- **Decisions API:** a **predicate**, "attack?", with p, plus a **choice** for severity. This is the canonical fit.
- **Cost:** 1,000 × ~800 tokens = 0.8M input → $0.08 per run. **Under $2 a month.**

### Idea 5: SQL incident-investigation agent (ExCyTIn-style)

- **Value:** the most "agentic" defensive task. It teaches multi-step tool use, context management and memory, and loop variants (ReAct, Reflect). There is a public leaderboard with open-weight rows to compare against (Qwen3-32B 0.182, Llama4-Maverick 0.290).
- **Plugins:** `dsh-sql-logs` (tool: read-only MySQL query with a row cap and timeout); memory plugin ([#11](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/11)) for findings; `ctx.decisions` as a stop/answer gate.
- **Data:** ExCyTIn-Bench. Start with **one incident database (~0.45 GB)**, not all 8.
- **Eval:** Promptfoo with a custom provider running the dsh headless CLI per question; the assertion is ExCyTIn's reward (exact or partial answer match). Run 50–100 test questions.
- **Decisions API:** a **predicate**, "enough evidence to answer?", to stop early, or a **choice** among the agent's candidate answers.
- **Cost:** ~15 steps × ~8k tokens ≈ 120k input per question; 100 questions ≈ 12M input plus ~0.5M output → about $0.55 listed or about $4.2 mainstream for deepseek-v4.1-flash per run. **About $5–15 a month** at 2–3 runs. **The most expensive idea; cap the steps.**

### Idea 6: Dependency exploitability triage (VEX)

- **Value:** it teaches SBOMs, OSV and reachability, and the difference between "vulnerable dependency" and "exploitable here."
- **Plugins:** `dsh-osv` (tool: osv-scanner in offline mode, JSON out; call analysis where supported); built-in fs tools for code search; `ctx.decisions`.
- **Data:** VEX-Bench (75 labelled cases; check its license first). Plus your own repos for real use.
- **Eval:** Promptfoo; binary F1 and justification macro-F1, compared with the paper (frontier about 80% F1).
- **Decisions API:** a **choice** of VEX status (`not_affected`, `affected`, `fixed`, `under_investigation`) plus a choice of justification.
- **Cost:** ~10 steps × ~10k tokens ≈ 100k per case × 75 = 7.5M input → about $0.30 listed or about $2.5 mainstream per run. **About $3–8 a month.**

### Idea 7: Diff-based security reviewer with a false-positive pass

- **Value:** it rebuilds Anthropic's reviewer pattern (review → separate FP filter) on open models and measures it honestly against PrimeVul's "near random" finding.
- **Plugins:** `dsh-sec-review` (tools: get diff, fetch a function or class on demand, Vulnhuntr-style); optional Semgrep/CodeQL tool as candidate generator; `ctx.decisions` for the FP filter.
- **Data:** PrimeVul **paired** test functions (vulnerable vs fixed) and CVEfixes before/after functions (CC BY 4.0).
- **Eval:** Promptfoo; pair-correct rate (both halves of a pair right) and FP rate; with and without the FP-filter stage.
- **Decisions API:** a **predicate**, "is this finding a true vulnerability?", on each candidate finding.
- **Cost:** 300 pairs × 2 × ~2k tokens = 1.2M input plus reasoning output → about $0.5–2 per run. **About $2–6 a month.**

### Idea 8: Verified patch suggestion for SAST findings (Autofix-style)

- **Value:** it closes the loop from finding to fix, with a **verifier**: re-run the scanner, run the tests. It teaches sandboxing and the "patch hides the crash" failure mode (AutoPatchBench).
- **Plugins:** `dsh-autofix` (tools: run Semgrep or CodeQL → SARIF; apply a patch; run tests in Docker or Daytona); `ctx.decisions` to rank candidate patches.
- **Data:** BaxBench (MIT, has an OpenRouter flag; use its exploits as the security oracle). Or CVEfixes commits whose repos have tests. **Skip SEC-bench and AutoPatchBench on the MacBook** (more than 200 GB of images, C/C++ builds).
- **Eval:** Promptfoo, with the Copilot Autofix checks as assertions: alert gone, no new alerts, it compiles, tests unchanged.
- **Decisions API:** a **choice** among N candidate patches, or a predicate "does the patch preserve behaviour?" A weak fit; the verifier is the real judge.
- **Cost:** ~8 steps × ~10k tokens per finding × 40 findings ≈ 3.2M input → about $0.15 listed or $1.5 mainstream per run, plus BaxBench generation. **About $3–10 a month.**

### Suggested order (opinion)

1. Idea 1 or Idea 2: classification, Decisions and Promptfoo basics.
2. Idea 4: calibration in a real SOC job.
3. Idea 3: a tool loop with a deterministic verifier.
4. Idea 5 or Idea 6: a multi-step investigation agent.

Ideas 7 and 8 are good AppSec alternatives if [#22](https://github.com/ZeleMate/DeepSeek-demo-implementation/issues/22) leans AppSec.
